| | `DELETE FROM 表` | `TRUNCATE TABLE 表` |

| 约束 | 管什么 |
|---|---|
| `PRIMARY KEY` | 唯一且不为空 |

## 建表和约束

### `CREATE TABLE` + 约束

- 作用：建表时写上列类型和约束，让数据库替你挡住坏数据
- 说法：建表；加约束；不允许重复；不能为空
- 分类：建表和约束
- 项目：练习：student / course / sc；豆瓣：7 张规范化表；Steam：`game_group`、`game`、`player_count`
- 坑：约束只管“存在的数据对不对”，管不了“该有的数据有没有”，比如“某部电影一个类型都没有”约束挡不住

### 联合主键 `PRIMARY KEY (列1, 列2)`

- 作用：两列合起来唯一
- 说法：多对多中间表的主键；同一组合不能重复
- 分类：建表和约束
- 项目：豆瓣：`movie_genre (movie_id, genre_id)`；Steam：`player_count (game_id, collected_at)`，同一游戏同一小时只能有一条
- 坑：联合主键的中间表没有自增 id

### 1NF、多对多、中间表

- 作用：一个格子只放一个值；多对多关系拆成两张实体表 + 一张中间表
- 说法：一个字段存了多个值；拆表；规范化
- 分类：建表和约束
- 项目：豆瓣：`country`、`genre` 一格多个值，拆成 `movie_new`、`genre`、`country` + 两张中间表，后来加了 `director` + `movie_director`

### `FOREIGN KEY` 与删除顺序

- 作用：子表的外键必须指向父表里存在的行
- 说法：外键；关联约束；删不掉
- 分类：建表和约束
- 项目：豆瓣：`split_tables.py` 先 `DELETE` 三张中间表，再删 `movie_new`、`genre` 等
- 坑：中间表还有记录指着某部电影时，不能先删那部电影；顺序反了会报错

### `CHECK (条件)`

- 作用：自定义约束
- 说法：至少有一个不为空；限制取值
- 分类：建表和约束
- 项目：豆瓣：导演表 `CHECK (name_cn IS NOT NULL OR name_en IS NOT NULL)`，中英文名至少有一个

### `UNIQUE`

- 作用：这一列不允许重复
- 说法：不能重名；唯一
- 分类：建表和约束
- 项目：豆瓣：`genre.name`、`country.name`、`director.name_cn` / `name_en`

## 改数据和事务

### `INSERT` / `UPDATE` / `DELETE`

- 作用：插入、修改、删除行
- 说法：插数据；改数据；删数据
- 分类：SQL 改数据
- 项目：练习；豆瓣：`split_tables.py` 先清表再插入，所以可以反复重跑
- 坑：`UPDATE`、`DELETE` 忘写 `WHERE` 会改动整张表

### `DELETE FROM 表` vs `TRUNCATE TABLE 表`

- 作用：都能清空表；`DELETE` 不重置自增计数，`TRUNCATE` 重置
- 说法：清空表；自增 id 不从 1 开始；id 越来越大
- 分类：SQL 改数据
- 项目：豆瓣：每次重跑拆表，`movie_new` 的 id 都往上涨，读出来从 2003 开始
- 坑：这不影响使用，id 本来就不该有业务含义

### `START TRANSACTION` / `COMMIT` / `ROLLBACK`

- 作用：一组操作要么全成功，要么全撤销；MySQL 默认自动提交
- 说法：事务；全成或全败；撤销操作；回滚
- 分类：SQL 改数据
- 项目：练习：转账例子；ACID 是原子性、一致性、隔离性、持久性

## 索引

### `CREATE INDEX 名 ON 表(列)` / `SHOW INDEX FROM 表` / `DROP INDEX 名 ON 表`

- 作用：给常用来查询的列建索引；查看；删除
- 说法：加索引；查询太慢；看表有哪些索引
- 分类：建表和约束
- 项目：练习：`idx_表名_列名` 命名
- 坑：主键自动就是索引；索引不是越多越好，会拖慢增删改

### `EXPLAIN SELECT ...`

- 作用：看查询打算怎么执行；看 `type`（`ALL` 是全表扫描）、`key`（用了哪个索引，`NULL` 是没用）、`rows`（预计扫多少行）、`key_len`
- 说法：查询走没走索引；执行计划；为什么慢
- 分类：SQL 查询
- 项目：练习：自己跑出过 `type=ref`
- 坑：表只有几行时，优化器可能故意不用索引，这是正常的

### 索引失效

- 作用：索引列要“干干净净”地出现在条件里
- 说法：建了索引还是慢；索引没用上
- 分类：SQL 查询
- 项目：练习
- 坑：对索引列用函数或运算（`YEAR(日期) = 2024`、`score + 10 > 90`）、`LIKE '%三'` 以 % 开头、`!=` / `NOT IN` 等、隐式类型转换（数字列用字符串比）

## 数据检查和导出

### 断言式检查：查出行就是有问题

- 作用：每条检查是一句专门找坏数据的 SQL，0 行 = 通过；计数类检查用 `HAVING` 统一成同样的规则
- 说法：数据质量检查；校验数据；有没有脏数据
- 分类：SQL 查询
- 项目：豆瓣：`check.py` 7 条：总数 250、片名为空、评分越界、年份格式、没类型 / 国家 / 导演
- 坑：检查本身也要检查：用 `UNION ALL` 造假数据，或临时改条件故意让它失败，确认它真的能抓到问题

### `mysqldump --no-data`

- 作用：只导出表结构，不导数据
- 说法：导出建表语句；表结构存成文件；备份结构
- 分类：建表和约束
- 项目：豆瓣：`--no-data --skip-add-drop-table --skip-dump-date --ignore-table=douban.movie` 导出成 `schema.sql`，再用 sed 去掉 `AUTO_INCREMENT=`
- 坑：默认带 `DROP TABLE IF EXISTS`，在有数据的库上一跑全没了；`movie` 表由爬虫自己建，不进 `schema.sql`（谁生成数据，谁定义结构）

### `FOREIGN_KEY_CHECKS=0` / `/*!40014 ... */`

- 作用：mysqldump 文件开头暂时关掉外键检查，因为按字母顺序建表，子表可能排在父表前面；`/*!版本号 ... */` 是 MySQL 会执行、别的数据库当注释的写法
- 说法：导入时外键报错；建表顺序
- 分类：建表和约束
- 项目：豆瓣：把 `schema.sql` 导进测试库没有报错，原因就在文件开头
